The Shift

UX is now Product Experience.
The name change matters.

User Experience was about designing for users — making things usable, learnable, accessible. Product Experience is about designing for buyers of a product — building something people want to buy that is also usable, consistent, accessible, and trustworthy.

The function is evolving into a hybrid of design, engineering enablement, and operations. We create the ability for anyone to ship ideas quickly — prototypes, structured starter code in tickets, minimum UI standards baked into the tooling — so the handover to engineering is faster and cleaner, not slower.

But the UI is the easy part. The harder problems — user journeys that actually work, edge cases that don't break trust, consistency across products, accessible experiences that pass procurement — are where Product Experience makes the difference between shipping fast and shipping well.

The deal is simple: we build the rules into the tools so anyone can ship with as much or as little UX support as they want. In return, everything that ships gets reviewed — retrospectively if it has to be — for consistency, usability, and accessibility. Speed up front, quality assurance behind.

Product Experience owns the standards, the tooling, and the quality floor that let the whole organisation ship UI fast — and as the platform becomes more agentic, we own how it behaves, not just how it looks.

Responsibilities

Seven things we're accountable for.

01Enable anyone to ship fast. AI capabilities, design system, and coding standards that let anyone create and ship with quality baked in.
02Elevate what gets shipped. Where gaps remain, we identify them and work with Product and Engineering to close them — directly in repos where possible, not through handover documents. Every fix follows the same process as any engineering contribution — tracked in JIRA, reviewed by code owners, subject to the same automated quality gates.
03Own the design system as infrastructure. The single foundation for consistent, accessible UI at speed.
04Own the quality floor. The minimum standard below which we don't ship — not a gate, a measurable bar.
05Ensure accessibility by design. Commercial risk management for regulated procurement, not a design preference.
06Keep research embedded and continuous. Lightweight, continuous, focused on what only human judgment can answer.
07Define how the product behaves. How it earns trust, communicates confidence, and hands control back to humans.

Operating Model

Four ways to work with us.

Product Experience operates like AppSec does for security — automated enforcement of the baseline, a consulting function teams can call on, and an independent improvement cycle that keeps the product getting better. Not everything needs a designer. But everything that ships gets better over time. Here's how to know which route your work takes.

01
Self-Service
The default — any PM, developer, or exec
Use the skills, component library, and approved patterns to build and ship. The quality standards are in the tooling — 80% BSDS compliance by default. UX reviews everything that ships and feeds improvements back into the tools and the roadmap. This is how most work should flow. If in doubt, start here.
02
Rapid UX Review
After delivery — fixing what shipped
UX reviews directly in the product repo. We fix custom UI, layout issues, and consistency gaps in code. Each fix also improves the plugin — same problem can't recur. If Self-Service output doesn't meet the quality floor, this is where it lands.
03
UX Concept
When you need a design direction before building
UX delivers a quick concept prototype based on an initiative or brief. Others take it forward and build the product from it. We review what ships and close gaps afterwards.
04
Embedded Product Experience
Reserved for: new, complex, or trust-critical
UX involved from the start. New interaction paradigms, trust-critical AI behaviours, cross-product journeys. The work where getting it right first time saves the most rework later. This is the exception, not the rule — reserved for work where the cost of getting it wrong significantly exceeds the cost of designing upfront.
The flywheel: Every retroactive fix produces two outputs — the fix itself, and a system improvement (a new component, plugin rule, or pattern) that prevents the same problem recurring. The metric that proves it works: fewer issues each quarter because the tooling caught them first.

AI Trust

Nine principles for how our AI behaves.

As the platform becomes more agentic, someone needs to own how it communicates confidence, handles uncertainty, and hands control back to humans. Product defines the logic. UX defines the expression.

01Confidence — How sure is the AI? Does it tell you?
02Control — Can you stop it, override it, or undo it?
03Reasoning — Does it explain why, not just what?
04Provenance — Where did it get its information?
05Persona — One consistent voice across every product.
06Agency — Is it suggesting or doing? Do you know which?
07Feedback — Can you tell the AI it was wrong?
08Recovery — Can you undo, reject, or override what it did?
09Data Handling — Does it protect sensitive information?
IBM and Microsoft have already shipped frameworks for exactly this. We're behind — but the fix isn't rebuilding three products, it's agreeing on nine rules and applying them consistently.

Quality Floor

The minimum standard below which we don't ship.

31

36
Documented for AI
46
AI skills enforcing standards

Six rules define the floor. Below any of them, the work moves from Self-Service to Rapid UX Review — Product Experience gets involved.

0180%+ BSDS component usage. At least 80% of UI built from library components, not custom.
02Zero inline styles. No inline style attributes anywhere in the UI.
03Zero hardcoded tokens. No hardcoded colours, spacing, or typography values.
04No unjustified custom components. Every custom styled-component must be justified and registered.
05Zero critical accessibility violations. BSDS components handle this by default. Custom work must pass the same bar.
06Standard page layout. Every page uses PageLayout. No invented navigation or shell chrome.
Quality should be inherited, not inspected. The standards are in the tooling, not in our heads.

Ongoing

BSDS alignment across all product repos. We deliver structured code in tickets based on the latest library versions — the goal is every repo running the same version of every component.

The ask

Use the four routes. Start with self-service. Bring us in when it matters. Let the system work.

The ask to Product

The operating model works when iteration is protected. MVPs ship fast — that's the point. But the six-month view needs roadmap space, not just goodwill. Product Experience will raise the tickets, make the case, and track the debt. Product needs to commit to a proportion of capacity for iterative improvement — not as a favour, but as the mechanism that keeps the product getting better after first release.

One thing to note

The operating model's structure works with and without AI tooling — the four routes, the quality floor, and the embedding model don't depend on it. AI makes self-service viable at scale and makes every route faster. If AI availability is constrained, the model still holds — it just runs at a different speed.

This isn't about defending UX's existence. It's about making the whole organisation ship faster and better — and making sure the product earns trust as it becomes more autonomous.
